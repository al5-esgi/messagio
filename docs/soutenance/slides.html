Séances 1–3 · Cadrer, rattraper, authentifier

Le framing

TCP livre un flux d'octets. 4 octets de longueur, puis le contenu : on n'émet rien tant que la trame est incomplète.

SSE rattrapable

Buffer borné, rejeu par Last-Event-ID, resync-needed si le retard le dépasse.

Le handshake

Une WebSocket commence par un GET HTTP. Le serveur répond 101, et la socket cesse d'être HTTP.

Après le 101, plus jamais d'en-têtes : le handshake est le seul moment où l'on peut authentifier une connexion.

401 = identité (JWT) · 403 = provenance (Origin) · 1008 = 15 msg/s dépassés. Et l'auteur vient du JWT, jamais du corps : mallory qui envoie "auteur": "usurpateur" est enregistré mallory.

[1:05 → 2:05] SSE a été implémenté en sachant qu'il ne serait pas retenu : unidirectionnel, un « X écrit… » imposerait un POST par frappe. Mais son mécanisme de rattrapage est celui que je rejoue en séance 6. Le point fort ici : authentifier la connexion ne sert à rien si le corps du message reste libre.

Socket.IO n'est pas WebSocket

C'est un protocole applicatif au-dessus, avec son propre encodage. D'où l'obligation d'un client dédié : new WebSocket(...) ne s'y connecte pas.

Ce qu'il ajoute

  • rooms — diffuser à un sous-groupe
  • acks — requête/réponse sur un canal bidirectionnel
  • reconnexion avec backoff, et heartbeat
  • adapter — plusieurs instances (séance 7)

Ce qu'il coûte

  • protocole non standard, client imposé
  • surcoût d'encodage par message
  • une room ne survit pas à une reconnexion

Retenu parce que rooms + acks + adapter sont exactement les trois choses que j'aurais dû réécrire sur ws nu.

[2:05 → 3:15] Définir l'ack : un callback qui voyage avec l'événement — la fonction n'est pas transmise, seul un numéro de corrélation l'est. TCP garantit les octets, WebSocket la trame, l'ack garantit que l'application a accepté. Enchaîner sur la slide suivante : ce que les rooms règlent.

Séance 6 · Convergence

Un chat est un journal d'événements immuables, pas un état mutable partagé. Personne n'édite le message d'un autre — la transformation d'OT ne servirait jamais.

Le renversement : de « calculer exactement ce qui manque »
à « renvoyer largement, il triera ».

Un problème de calcul exact devient un problème d'idempotence ; le seq en est la clé, et le renvoi cesse d'être dangereux.

npm run scenario → code 1, doublons -- --avec-strategie → code 0, converge

Limite : la déduplication ne comble pas les trous. Recevoir les seq 1 et 5 affiche 1 et 5 — rien n'est inventé.

[4:15 → 5:10] Ce que ça débloque : referme le trou de la séance 4 — quand un ack se perd, on ne savait pas si le message était passé, et renvoyer produisait un doublon.

WebRTC : pair-à-pair, mais pas sans serveur

Deux navigateurs ne se connaissent pas. Il faut un tiers pour qu'ils échangent de quoi se joindre : c'est le signaling, et c'est tout ce que fait le serveur.

SDP

La description de ce qu'on sait faire : codecs, pistes, chiffrement. Échangée en offer / answer.

ICE

Les chemins possibles. host = adresse locale, srflx = adresse publique vue par un STUN.

TURN

Le repli quand le NAT bloque : un serveur relaie le flux — et réintroduit le tiers qu'on voulait éviter.

Une fois le canal ouvert, les données ne passent ni par le serveur ni par Redis. Mais il n'y a plus d'autorité : ni seq, ni historique, ni rattrapage.

D'où l'ADR-1 : WebRTC pour la visio seulement. Et la même règle d'autorisation que le salon, sinon la room d'appel serait une porte dérobée.

[6:10 → 7:20] Le paradoxe « pair-à-pair mais serveur obligatoire » est le point à faire passer. Si on me demande le piège rencontré : createDataChannel et addTrack déclenchent tous deux onnegotiationneeded — émettre aussi une offre à la main fait entrer les deux négociations en collision.

Trois décisions — et ce qui manque

1Socket.IO pour le flux principal Pas SSE : unidirectionnel. Pas WebRTC : aucune autorité centrale.
2seq + déduplication Pas OT ni CRDT : un message est atomique, la transformation ne servirait jamais.
3Reconnexion + resync Redis rend le scaling possible, pas le système résilient.

Limites connues : les seq sont en mémoire — un redémarrage les recycle et un client peut croire son état à jour à tort. Les trous ne sont pas encore détectés activement. Et /api/dev-token n'authentifie personne.
